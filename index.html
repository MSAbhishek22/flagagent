THE PROBLEM

Flag changes are easy to make and hard to review.

The dashboard sprawl

One rollout touches flags, environments, segments and splits across half a dozen screens. Each screen is a chance to change the wrong thing in the wrong place.

Agents with write access

Give an agent an API key and it can move every switch you own, silently, at machine speed. One misread sentence becomes a production incident.

No receipt

After a change lands, proving what actually changed — and that it matches what was asked for — means digging through audit logs by hand.

HOW FLAGAGENT WORKS

Plan first. Approve second. Apply last.

01

It plans, read-only

Your sentence becomes a list of exact changes — flag, environment, before and after — checked against the traps: variant weights that do not add to 100, a flag name already taken, a guard already broken.

02

You approve, change by change

Every change is its own line with its own tick box. Reject one and it never happens. A delete needs the flag's name typed out. The plan carries a short hash, so what you approved is what runs — or nothing runs.

03

It applies, then proves it

Approved changes go to Flagsmith in order. Each one is read back and compared with the plan before it is called done. Guards are checked again at the moment of applying — if a guard broke while you were reading, everything stops.

The gate is the product. Planning never writes. Applying needs your ticks, your typed name for a delete, a matching plan hash and holding guards — all four, every time.
